Know which agent needs you.

Claude Mate is a tiny desk device that cuts the cognitive overload of orchestrating many Claude Code sessions at once — across different accounts and projects. One glance tells you which session finished, is blocked, or errored; one button takes you straight to it.

The problem it solves

Running a fleet of agents means a wall of terminals, each on its own schedule. The tax isn't the work — it's watching for which one stalled. Claude Mate moves that watching off your screen and onto one calm surface.

🗂️

One triage queue

Every session in a stable, alphabetical order — tabs never shuffle under you. Different accounts and projects, one list.

💡

An LED that means it

A status-distinct blink for the worst unacknowledged alert — finished, waiting, or errored — looping until you deal with it.

⏎

One button, there

Press GO and the exact terminal for the session on screen is raised. No hunting across windows.

What's on the glass

One pre-composed screen — the selected session over a whole-fleet strip. The daemon renders the same four rows for both devices; each just draws what it was sent. Buttons never change meaning: PREV · GO · NEXT, plus MIRROR on the S3.

See the terminal, not just the status

The fourth key on the S3 opens a live view of the selected session’s actual terminal — 52×17 characters, refreshed about once a second. PREV/NEXT scroll it; GO closes it and raises the real window. This is the one thing three buttons could not do.

device · bluetooth

The device is the gamepad

With Claude Mate linked, the four keycaps drive the game on screen — the same four switches that step the triage queue, with nothing re-flashed and nothing re-wired. PREV and NEXT walk, GO jumps and holds for height, the fourth key goes back to the menu. The badge over the screen turns green when the device has the controls.

Two ways, and one of them works right here. Pair the device over Bluetooth (SETTINGS → BLE gamepad) and it becomes an ordinary system gamepad — no daemon, no install, and no localhost, so it drives this page like any other controller. The older path is the daemon run with --web and the game opened from http://127.0.0.1:8788; that one is local only, because a page served over https cannot talk to a local http server.

no hardware

The keyboard works for everyone

No device, no daemon, no install: ← → to walk, ↑ to jump, esc for the menu (A / D / W and space do the same). That is the entire requirement, and it is how most people will play it — the game was tuned in a browser long before it ran on hardware.

Coyote time and jump buffering are in, because playing it proved they had to be: the launch window for a gap is about eight frames, and without them only one timing in five cleared the first jump.

The same game also runs on the S3, from the device's own menu — same numbers, same jump arc, and the record survives a flat battery. Twelve milestones are designed and one is built, which is the first thing on the list below.

Parts

Two builds, one protocol — the daemon cannot tell them apart, and both can be connected at the same time. Full pinouts in firmware/README.md and docs/WIRING.md; the bill of materials lives in the README.

Iteration 2 — ESP32-S3, cordless

  • 1×Waveshare ESP32-S3-LCD-1.47B — 172×320 IPS, 8 MB PSRAM, 16 MB flash, USB-C. Carries the WS2812, the charger and the battery divider
  • 4×Kailh Choc low-profile (1350) switches — PREV · GO · NEXT · MIRROR, on GPIO 3–6
  • 4×Choc keycaps — any low-profile cap that fits Choc stems
  • 1×14500 Li-ion cell, ~800 mAh — AA-sized 3.7 V, straight into the board’s header
  • 2×M2 screws — close the printed enclosure
  • 1×USB-C cable — flashing and charging

No resistors, no debounce caps, nothing to solder on the board side — the firmware debounces in software and the four switches share one ground. The cell must be 3.7 V Li-ion: the onboard charger and the gauge curve are calibrated for that chemistry.

Iteration 1 — Arduino Nano, USB

  • 1×Arduino Nano (ATmega328P) — any USB-serial clone works
  • 1×SSD1306 0.91″ 128×32 OLED, I²C — addr 0x3C; 0.96″ 128×64 also works
  • 3×Momentary push buttons — PREV · GO · NEXT (INPUT_PULLUP)
  • 1×Indication LED + ~220 Ω–1 kΩ resistor — on D8, the sole alert output
  • 1×USB cable — data-capable, to the Mac
  • —3D-printed enclosure — printable model below

Software: a Python daemon (pyserial) on macOS. Firmware libraries: Adafruit GFX for the Nano (the SSD1306 is driven by a bundled software-I²C driver), and Arduino_GFX for the S3.

Build it & make it yours

Print the enclosure, wire the switches, flash the firmware, run the daemon. Photos and both printable models are in the repo’s assets. The S3 needs ./firmware/flash_s3.sh — arduino-cli upload genuinely cannot flash that board, and the firmware README explains the three reasons why.

Roadmap

Built in iterations, each removing more friction than the last. The goal never changes — one calm surface that tells you which agent needs you.

Iteration 1 · shipped

Arduino + macOS

An Arduino Nano drives the OLED, buttons, and LED over USB serial; a Python daemon on the Mac keeps the queue, renders the screen, and raises windows. Unchanged and still supported — and it can be plugged in alongside the S3.

Iteration 2 · now

ESP32-S3 Wi-Fi remote

The device reaches the daemon over Wi-Fi instead of USB — a genuinely wireless desk remote you can put anywhere, on a 14500 cell with a battery gauge and a deep-sleep power-off. The colour LCD brought colour-coded alerts and a fourth key: the live terminal mirror.

The goal stays fixed across every iteration: one calm surface that tells you which agent needs you, so running many of them in parallel stops taxing your attention.

Take a piece of it

Not "PRs welcome" — a list of things the design specifies and the code does not do yet, each with what it actually costs you and the file it lives in. Two of them need no hardware and no Mac at all.

start here · no hardware

Draw a level

Twelve milestones are designed; one is built. A level is a plain 7 × 108 character grid — . is a day you shipped nothing, 1–4 are the four greens — and level 1 ships as exactly that. Two measured rules bound anything you draw: a jump clears two tiles across and rises one row, so every raised ledge needs one step per row it climbs.

docs/GAME.md §4 level_01.h

a weekend · no hardware

Write the reachability checker

The design asks for it in so many words: a real breadth-first search from the spawn point over standing positions, not a per-tile sanity check — a ledge always looks fine next to its own neighbours. The first pass at level 1 left all seventeen pull requests unreachable, and only playing it found that. Nothing in tools/ does this yet.

docs/GAME.md §2 tools/

harder · C++ or JS

Build an enemy that only exists on paper

Five enemy types are specified; two are implemented. The flaky test blinks in and out on a fixed cycle, the merge conflict is static and must be routed around, the regression comes back once, angrier. Each also owes a codex card — every enemy freezes the game to introduce itself, because nobody should learn a rule by losing a day to it.

docs/GAME.md §5 game/ship_it.h

small · needs a Mac

Teach the detector a new terminal

Session state is scraped from the live Claude Code TUI using substrings in patterns.json, hot-reloaded in about a quarter of a second with no restart. An unusual theme, a non-English locale or a new picker phrase needs one line — and the file documents its own precedence and the traps, because a match that is too loose is worse than none.

real work · a port

Get the daemon off macOS

The README says it plainly: serial device naming, open and the AppleScript window raise are Mac-specific. The line protocol, the queue and both firmwares are not — the device cannot tell what is on the other end of the wire, which is the whole reason a port is a bounded job rather than a rewrite.

docs/ARCHITECTURE.md docs/PROTOCOL.md

hard · needs the S3

Spike the panel's hardware scroll

The LCD sits on non-IOMUX pins, so the bus is capped at 40 MHz, the SPI driver is polled rather than DMA, and every flush pushes all 110 KB: ~28 ms, a ~30 fps ceiling before a single line of game logic. The ST7789's own scroll registers would move the world for free in this rotation — but Arduino_GFX does not expose them, so it is a bench experiment, not a plan.

Before the first pull request. The project is CC BY-NC 4.0 — personal and non-commercial, and contributions come in on the same terms. The CLA is one sentence in your first PR, and CONTRIBUTING.md explains why it exists rather than asking you to take it on faith. One naming rule: no new identifier may contain "claude" or "anthropic" — prose is fine, identity is not.

Or just build one

Four steps, and the only soldering is four switches to a header. The repo names the exact parts and deliberately quotes no prices — what they cost depends entirely on where you buy them.

  1. 1Print the enclosure — claude_mate_s3.stl: body, 1 mm faceplate, LCD shelf and rim, ≈ 55 × 43 × 23 mm. The Nano's enclosure is a .3mf.
  2. 2Get the parts — one Waveshare ESP32-S3-LCD-1.47B, four Kailh Choc switches and keycaps, one AA-sized 14500 Li-ion cell, two M2 screws, a USB-C cable and some hook-up wire. No resistors, no debounce caps, nothing to solder on the board side. Full BOM →
  3. 3Wire and flash — four switches to GPIO 3–6 and one shared ground, then ./firmware/flash_s3.sh: arduino-cli upload genuinely cannot flash this board, and the firmware README gives the three reasons. Wiring → Firmware →
  4. 4Run the daemon and the hooks — Python 3.9+ and one dependency, pyserial; install/install.sh templates the LaunchAgent and loads it. Start with --mock if the hardware hasn't arrived yet. Install →

Iteration 1 is the cheaper way in and is still supported: an Arduino Nano, a 128×32 OLED, three buttons and one LED. Both builds speak the identical protocol, so whatever you contribute to the daemon has to keep working for the Nano — which is a constraint, and also the reason the project has stayed simple.
