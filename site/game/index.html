SHIP IT is a small platformer that runs in your browser. The terrain is a contribution graph — a day you shipped something is a tile you can stand on, a day you shipped nothing is a hole you fall through. You get no lives. You get days until the milestone, and every bug that reaches you eats one.

device · local only

The device is the gamepad

With Claude Mate linked and the daemon running, the four keycaps drive the game on screen — the same four switches that step the triage queue, with nothing re-flashed and nothing re-wired. PREV and NEXT walk, GO jumps and holds for height, the fourth key goes back to the menu. The badge over the screen turns green when the device has the controls.

Honestly, and by construction: that path needs the daemon run with --web and the game opened from http://127.0.0.1:8788, on the machine the device is linked to. A page served over https cannot talk to a local http server, so the copy you play from this site is the keyboard one.

no hardware

The keyboard works for everyone

No device, no daemon, no install: ← → to walk, ↑ to jump, esc for the menu (A / D / W and space do the same). That is the entire requirement, and it is how most people will play it — the game was tuned in a browser long before it ran on hardware.

Coyote time and jump buffering are in, because playing it proved they had to be: the launch window for a gap is about eight frames, and without them only one timing in five cleared the first jump.

start here · no hardware

Draw a level

Twelve milestones are designed; one is built. A level is a plain 7 × 108 character grid — . is a day you shipped nothing, 1–4 are the four greens — and level 1 ships as exactly that. Two measured rules bound anything you draw: a jump clears two tiles across and rises one row, so every raised ledge needs one step per row it climbs.

a weekend · no hardware

Write the reachability checker

The design asks for it in so many words: a real breadth-first search from the spawn point over standing positions, not a per-tile sanity check — a ledge always looks fine next to its own neighbours. The first pass at level 1 left all seventeen pull requests unreachable, and only playing it found that. Nothing in tools/ does this yet.

harder · C++ or JS

Build an enemy that only exists on paper

Five enemy types are specified; two are implemented. The flaky test blinks in and out on a fixed cycle, the merge conflict is static and must be routed around, the regression comes back once, angrier. Each also owes a codex card — every enemy freezes the game to introduce itself, because nobody should learn a rule by losing a day to it.

docs/GAME.md §5 game/ship_it.h

small · needs a Mac

Teach the detector a new terminal

Session state is scraped from the live Claude Code TUI using substrings in patterns.json, hot-reloaded in about a quarter of a second with no restart. An unusual theme, a non-English locale or a new picker phrase needs one line — and the file documents its own precedence and the traps, because a match that is too loose is worse than none.

real work · a port

Get the daemon off macOS

The README says it plainly: serial device naming, open and the AppleScript window raise are Mac-specific. The line protocol, the queue and both firmwares are not — the device cannot tell what is on the other end of the wire, which is the whole reason a port is a bounded job rather than a rewrite.

hard · needs the S3

Spike the panel's hardware scroll

The LCD sits on non-IOMUX pins, so the bus is capped at 40 MHz, the SPI driver is polled rather than DMA, and every flush pushes all 110 KB: ~28 ms, a ~30 fps ceiling before a single line of game logic. The ST7789's own scroll registers would move the world for free in this rotation — but Arduino_GFX does not expose them, so it is a bench experiment, not a plan.

Or just build one

Four steps, and the only soldering is four switches to a header. The repo names the exact parts and deliberately quotes no prices — what they cost depends entirely on where you buy them.

  1. 1Print the enclosure — claude_mate_s3.stl: body, 1 mm faceplate, LCD shelf and rim, ≈ 55 × 43 × 23 mm. The Nano's enclosure is a .3mf.
  2. 2Get the parts — one Waveshare ESP32-S3-LCD-1.47B, four Kailh Choc switches and keycaps, one AA-sized 14500 Li-ion cell, two M2 screws, a USB-C cable and some hook-up wire. No resistors, no debounce caps, nothing to solder on the board side. Full BOM →
  3. 3Wire and flash — four switches to GPIO 3–6 and one shared ground, then ./firmware/flash_s3.sh: arduino-cli upload genuinely cannot flash this board, and the firmware README gives the three reasons. Wiring → Firmware →
  4. 4Run the daemon and the hooks — Python 3.9+ and one dependency, pyserial; install/install.sh templates the LaunchAgent and loads it. Start with --mock if the hardware hasn't arrived yet. Install →

Iteration 1 is the cheaper way in and is still supported: an Arduino Nano, a 128×32 OLED, three buttons and one LED. Both builds speak the identical protocol, so whatever you contribute to the daemon has to keep working for the Nano — which is a constraint, and also the reason the project has stayed simple.
